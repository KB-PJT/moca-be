# Benefit Calculation Test

카드 약관의 계산 규칙을 실행 가능한 테스트로 고정한다. 정상 예시만 확인하지 말고 경계값, 미적용 사유,
CODEF 데이터의 불완전성과 재처리 상황까지 검증한다.

## 작업 순서

1. 현재 브랜치와 `git status`를 확인하고 관련 없는 변경을 보존한다.
2. 대상 카드의 약관, 상품 안내 또는 구조화 원본에서 `benefit_title`과 계산 조건의 근거를 확인한다.
3. 기존 계산 순서, 모델, 공통 Fixture, 동일 카드 테스트를 읽고 중복 구현을 피한다.
4. 먼저 룰을 아래 항목으로 분해하고 테스트 표를 만든다.
   - 혜택 유형과 단위
   - 계산 방식과 절사 정책
   - 적용 카테고리, 가맹점, 결제 채널
   - 최소 결제금액과 거래당 인정금액
   - 전월 실적과 신규 발급 유예
   - 일·월 횟수, 월 통합 한도
   - 시간, 요일, 승인일, 매입일 조건
   - 제외 거래, 취소, 환불, 중복 승인
5. 실패하는 테스트를 먼저 추가하고, 약관 근거에 맞춰 최소한의 구현만 변경한다.
6. 대상 테스트를 실행한 뒤 전체 `check`와 변경 상태를 확인한다.

약관이 모호한 조건을 임의로 계산하지 않는다. 계산에서 제외하고 정보성 안내로 둘 조건은 테스트에도 그 결정을
명시한다.

## 테스트 구조

- 범용 산식은 `BenefitCalculatorTest`처럼 계산기 단위로 검증한다.
- 카드별 규칙은 카드명과 `benefit_title` 기준으로 클래스를 분리한다.
  - 예: `MrLifeUtilityBenefitTest`, `MrLifeTimeBenefitTest`, `MrLifeWeekendBenefitTest`
- CODEF 정규화, 승인내역 재생, 혜택 역산은 카드 산식 테스트와 별도 클래스로 분리한다.
- 동일 카드의 공통 룰 생성과 금액 비교만 Fixture로 추출한다. 테스트 시나리오 자체를 Fixture에 숨기지 않는다.
- 한 테스트는 하나의 업무 규칙 또는 하나의 경계만 설명한다.
- 반복되는 동일 규칙의 경계표는 `@ParameterizedTest`를 사용하고, 서로 다른 업무 의미는 별도 `@Test`로 둔다.

클래스와 메서드에 한글 `@DisplayName`을 작성한다.

```java
@DisplayName("신한카드 Mr.Life TIME 할인 서비스")
class MrLifeTimeBenefitTest {

    @Test
    @DisplayName("21시 승인부터 Night 할인을 적용한다")
    void appliesNightDiscountFromNinePm() {
        // given
        // when
        // then
    }
}
```

주석은 약관 해석, 승인일과 매입일의 차이, CODEF 제약처럼 코드만으로 알 수 없는 이유를 설명할 때만 사용한다.

## 금액과 수량 검증

- 금액, 비율, 포인트, 마일리지와 소수 수량은 `BigDecimal`로 표현한다.
- `double`, `float`, `new BigDecimal(double)`을 사용하지 않는다.
- 테스트 값은 `new BigDecimal("0.10")`처럼 문자열로 만들거나 검증된 상수를 사용한다.
- `BigDecimal.equals`의 scale 차이로 실패하지 않도록 금액은 `compareTo` 기준으로 검증한다.
- 원 미만 절사, 반올림, 올림은 약관 또는 프로젝트 정책을 명시하고 경계값으로 고정한다.
- 거래당 인정금액 상한과 거래당 혜택금액 상한을 구분한다.
- `rawRewardValue`, `appliedRewardValue`, `remainingLimitValue`, `rejectionReason`을 함께 검증한다.
- 원화 할인만 결제금액을 초과하지 않는지 확인하고 캐시백·포인트·마일리지는 각 정책 단위로 검증한다.

## 필수 테스트 매트릭스

### 기본 산식

- `RATE`, `FIXED`, `PER_SPEND_UNIT`, `PER_USAGE_UNIT`
- 할인, 캐시백, 포인트, 마일리지와 각 `RewardUnit`
- 0원, 1원, 최소값 직전·일치·초과
- 비율 계산에서 소수점이 발생하는 값
- 결제 단위로 나누어떨어지지 않는 값
- 거래당 인정금액 직전·일치·초과
- 월 잔여 한도보다 계산 혜택이 작은·같은·큰 경우
- 한도 없음과 이미 소진된 한도

### 적용 자격

- 카테고리 일치와 불일치
- 가맹점 적격과 제외 가맹점
- 일반 결제와 지정 결제 채널
- 최소 결제금액 경계
- 전월 실적 각 구간의 `-1`, 경계값, `+1`
- 등록월과 익월의 신규 발급 유예, 유예 종료 직후
- 실적 제외 거래가 전월 실적에 포함되지 않는지

### 시간과 횟수

- 시작 시각 1초 전·정각, 종료 시각 1초 전·정각
- 금요일 23:59:59, 토요일 00:00:00, 일요일 23:59:59, 월요일 00:00:00
- 평일 공휴일을 주말로 오인하지 않는지
- 일 제한과 월 제한의 마지막 허용 건·첫 거절 건
- 여러 혜택이 통합 한도를 공유할 때 부분 적용과 완전 소진
- 승인 순서와 매입 순서가 다를 때 약관에서 정한 순서로 차감되는지

### 제외와 데이터 정합성

- 상품권, 세금, 수수료, 무이자할부 등 약관상 제외 거래
- 취소, 부분 취소, 전체 환불과 원승인 연결
- 동일 승인내역 재수집 시 중복 계산하지 않는 멱등성
- 승인 후 매입, 매입 취소, 지연 매입과 해외 매입일 기준
- 필수 값 누락, 알 수 없는 카테고리, 음수 금액, 잘못된 시간
- 수집 시작 이전 혜택을 확정값처럼 소급 계산하지 않는지

조건을 모델이나 데이터가 아직 표현하지 못하면 억지로 통과시키지 않는다. 누락된 모델을 테스트 이름과 실패 이유로
드러내고 구현 범위를 결정한다.

## CODEF 역산 검증

CODEF 승인내역에는 실제 할인·캐시백·포인트·마일리지 결과가 없으므로 다음 경계를 분리한다.

1. 외부 응답을 내부 승인 모델로 변환하는 정규화 테스트
2. 승인·매입·취소 내역을 정렬하고 중복 제거하는 재생 테스트
3. 구조화한 카드 룰로 혜택을 계산하는 산식 테스트
4. 할인·캐시백·포인트·마일리지 합계를 만드는 집계 테스트

전월 실적 응답값을 승인금액 합계와 혼동하지 않는다. 승인일과 매입일 중 어떤 값을 쓰는지 각 테스트에 드러내고,
같은 입력을 다시 처리해도 합계와 사용 횟수가 증가하지 않는지 확인한다. 역산값은 카드사 확정 혜택과 구분할 수
있어야 한다.

## 카드 데이터 검증

- 카드고릴라 `detail_html`은 계산 근거로 사용하지 않는다.
- 구조화한 `benefit_title`, 설명, 태그와 공식 상품 안내를 대조한다.
- `supported`, `partial`, `information_only`, `unsupported` 상태를 계산 가능 여부와 혼동하지 않는다.
- `partial` 룰은 구현된 조건과 미지원 조건을 각각 테스트한다.
- 200개 카드 전체를 복제 테스트하지 말고 산식 패턴별 대표 룰을 검증한다.
- 카드별 특수조건은 해당 카드와 `benefit_title` 테스트에 추가한다.
- 파서 또는 구조화 로직을 변경하면 알려진 카드의 golden fixture로 회귀를 확인한다.

## 완료 기준

- 정상 적용뿐 아니라 미적용 사유를 검증한다.
- 모든 임계 조건은 직전·경계·직후 값 중 필요한 조합을 포함한다.
- 새 계산 분기는 테스트에서 실행되며 JaCoCo 100% 하한을 만족한다.
- 테스트 이름만 보고 카드, 혜택, 조건, 기대 결과를 이해할 수 있다.
- `./gradlew test`와 `./gradlew check`를 통과한다.
- `git diff --check`, `git status`, staged diff를 확인하고 관련 없는 파일을 포함하지 않는다.
