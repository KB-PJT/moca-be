# GitHub 이슈와 Pull Request 작성

## 필수 절차

1. 이슈 내용을 작성하기 전에 반드시 아래 파일을 모두 읽는다.
   - `.github/ISSUE_TEMPLATE/parent.yml`
   - `.github/ISSUE_TEMPLATE/child.yml`
   - `.github/ISSUE_TEMPLATE/config.yml`
   - `.github/pull_request_template.md`
2. 요청이 부모 이슈인지 작업 이슈인지 판단한다. 단일 브랜치의 변경을 인계하는 경우에는 작업 이슈를 기본으로 작성한다.
3. 템플릿의 필수 필드와 순서를 그대로 사용해 내용을 작성한다. 필수 필드를 임의로 생략하거나 목록 형식으로 대체하지 않는다.
4. 부모 이슈와 연결된 작업 이슈 묶음은 하나의 브랜치와 하나의 Pull Request로 끝낼 수 있는 범위로 구성한다.
5. 부모 또는 작업 이슈 번호가 정해지지 않았다면 각각 `#부모 이슈 번호`, `#작업-이슈-번호`로 표시하고 임의의 번호를 만들지 않는다.
6. 사용자가 실제 GitHub 생성을 명시하지 않았다면 외부 상태를 변경하지 않고 복사 가능한 초안만 작성한다.

## Push 후 인계

사용자가 커밋과 push를 요청하면 다음 절차를 자동으로 수행한다.

1. 현재 브랜치명, `main` 이후의 커밋, `main` 대비 diff를 확인한다. 대화에서 언급된 계획이 아니라 실제 커밋된 변경을 기준으로 삼는다.
2. 변경 범위에 맞는 작업 이슈 제목과 본문을 작성한다.
3. Pull Request 제목은 대표 커밋과 변경 목적을 기준으로 `<type>(<scope>): 한글 요약` 형식으로 작성한다.
4. Pull Request 본문에는 관련 작업 이슈, 실제 작업 내용, 리뷰 포인트, 수행한 검증만 적는다.
5. 작업 이슈 번호를 알면 `Closes #번호`를 사용한다. 번호가 없으면 `Closes #작업-이슈-번호`를 사용하고 부모 이슈를 직접 종료하지 않는다.
6. push 결과와 함께 작업 이슈 초안과 Pull Request 초안을 한 번에 인계한다.

## 출력 형식

부모 이슈는 아래 제목을 순서대로 포함한다.

```markdown
## 📌 기능 요약
## 🎯 배경 및 목적
## 📂 구현 범위
## ✅ 완료 조건
## ⚠️ 고려 사항
## 📖 참고 자료
```

작업 이슈는 아래 제목을 순서대로 포함한다.

```markdown
## 🔗 부모 이슈
## 📌 작업 요약
## 📂 작업 내용
## ✅ 완료 조건
## ⚠️ 고려 사항
## 📖 참고 자료
```

Pull Request는 아래 제목과 구분선을 그대로 포함한다.

```markdown
## 관련 이슈

Closes #작업-이슈-번호

---

## 작업 내용

---

## 리뷰 포인트

---

## 체크리스트
```

## 작성 원칙

- 제목은 `<type>(<scope>): 한글 요약` 형식을 우선 사용한다.
- 완료 조건은 확인 가능한 체크리스트로 작성한다.
- 실제로 존재하는 문서·API·경로만 참고 자료에 넣고, 불확실한 정보는 가정이라고 표시한다.
- 사용자가 "내용만" 요청하면 GitHub 생성 절차나 라벨 설명 없이 붙여 넣을 수 있는 본문만 출력한다.
- Pull Request의 체크리스트는 실제 검증 결과에 맞춰 완료 여부를 표시하고 실행하지 않은 검증을 완료로 표시하지 않는다.
- 코드나 문서의 변경 범위를 부풀리지 않고 `main` 대비 diff에서 확인한 내용만 작성한다.
